# 项目架构与代码全面审计

审计日期：2026-09-04。对象：当前工作区，包含本次会话已经完成的 gpui-kit 迁移与本地 skill 清理；这些修改尚未提交。本报告是审计结果与实施建议，不表示所列问题已经修复。

## 结论

项目已经有合理的职责划分：确定性游戏规则独立于 UI，Adapter 的模型、规划、传输分离，音频集中管理。无需推倒重建，也没有充分理由引入 ECS、通用事件总线或大量小 crate。

主要问题在职责之间的边界：渲染回调同时承担运行时调度；状态变化与协议事件没有共同的归属；TCP 的响应优先级没有保护已经开始发送的帧；“缓冲区有上限”被当成了“单轮工作量有上限”。应优先修复这些问题，再做缓存和分配优化。

共列出 11 项需要处理的问题：2 项 P1、9 项 P2。P1 应在下一次发布前处理；P2 应纳入紧随其后的正确性与架构重构。另列出无需立即动手的优化机会，避免把静态推断当成已经测得的性能瓶颈。

## 按优先级排序的发现

### F01 · P1 · 响应可以插进已经发送一部分的 observation，破坏 JSON 帧

位置：[transport.rs:380](../../src/adapter/transport.rs#L380)，以及同文件 `flush_observation`。

`write_buf` 和 observation 的缓冲区/游标独立维护。`flush_writes` 总是先写响应，再续写 observation。如果前一轮 observation 已经部分写出，下一轮收到命令并生成 ack，ack 就会插在该 observation 的中间。TCP 允许短写和 `WouldBlock`，因此这是合法网络状态下的正确性问题。

**复现证据：**在临时测试中先发送 observation 的前 8 个字节，保留其剩余缓冲区，再入队一个 ack 并执行当前 flush。接收端第一行成为 `{"type":{"type":"ack",…}\n`，JSON 解析失败。测试构造的是合法的短写后状态，不依赖操作系统发送缓冲区恰好塞满。

**建议：**只允许一个正在发送的帧及其游标。已经开始的帧必须发送完毕，之后才能选择下一帧；可靠响应的优先级和 observation 的覆盖合并仅作用于尚未开始发送的帧。

**验收：**用可脚本化的 writer 注入短写、连续 `WouldBlock`、响应插入和连接关闭；检查所有输出行都可解析、可靠响应不丢失、未开始的 observation 可以合并。保留一个真实 TCP 冒烟测试即可，不把短写验证交给偶然的系统缓冲区压力。

### F02 · P1 · 游戏与 TCP 生命周期依赖窗口绘制

位置：[view.rs:99](../../src/ui/view.rs#L99)、[view.rs:176](../../src/ui/view.rs#L176)。

`render` 调用 `advance_frame`，后者完成手柄轮询、Adapter 接收和执行、固定步推进、observation 发送。窗口刷新不仅决定画面频率，也决定游戏和协议是否工作。

**证据级别：静态路径确认，尚未进行新的端到端遮挡实验。**当前依赖的 macOS GPUI 平台实现会根据窗口可见性控制 display link；`request_animation_frame` 不能作为可靠的后台协议调度器。窗口隐藏、最小化或系统节流可能拖慢或停止握手、控制命令和模拟。即使产品决定后台暂停游戏，连接服务也不应因此失去响应。

**建议：**提取明确拥有时钟、输入队列、GameState 和 Adapter 的运行时。通过 GPUI 执行器/计时任务推进，画面只读取快照并请求重绘；最初可以保持单线程，先解决调度归属，无需立刻给 TCP 增加线程。明确前台人工游戏与后台 Adapter 模式的暂停策略。

**验收：**窗口正常、失活、遮挡、隐藏和最小化时分别检查 hello/ack、运行步数与退出清理；后台暂停策略不能使协议超时或假报可玩。为运行时提供不创建窗口的集成测试入口。

### F03 · P2 · 每帧舍弃不足 1 ms 的时间，游戏速度受刷新率影响

位置：[view.rs:186](../../src/ui/view.rs#L186)。

每次用 `Duration::as_millis()` 截断 elapsed，然后立即把 `last_tick` 更新为当前时间。小数毫秒没有进入 accumulator，永久丢失；后续固定步累积无法补回。

**复现证据：**按当前计算方式输入约 60 秒的均匀帧间隔，60 Hz 和 120 Hz 仅推进约 57.6 秒，144 Hz 仅约 51.84 秒。数字来自理想时序探针，并非实际显示器帧率测量，但足以证明算法偏差。

**建议：**使用 `Duration` 或整数纳秒累积，减去固定步时保留余量；长时间停顿的追赶上限也在相同精度层处理。

**验收：**相同累计墙钟时间在不同刷新率、混合帧长、亚毫秒间隔下推进相同数量的固定步；单独验证有意的长停顿截断，避免将截断策略与精度损失混为一谈。

### F04 · P2 · 元素焦点不能代表窗口激活，失活时可能保留按键状态

位置：[view.rs:167](../../src/ui/view.rs#L167)、[events.rs:140](../../src/ui/view/events.rs#L140)。

目前仅以 `focus_handle.is_focused(window)` 判断是否丢失焦点。依赖实现中该检查比较窗口内部的 focus id，窗口是否 active 是另一份状态；应用切换时元素焦点可以保留。失活后收不到原按键的 key-up，就可能留下持续移动状态。与此同时，手柄仍无条件轮询，清空一次输入状态也不能阻止后台重新产生 held 状态。

**证据级别：**已核对调用链和依赖实现，未用真实键盘/手柄重新复现。

**建议：**订阅窗口激活状态变化，失活立即清理键盘与手柄保持状态；根据明确策略屏蔽非激活窗口的本地输入。不要借此停止 Adapter 的运行时服务。

**验收：**按住左右/软降后切换应用，在另一应用释放，再切回；并覆盖手柄持续按住、断连与重新激活。

### F05 · P2 · 切帧是平方复杂度，接入和事件处理缺少每轮预算

位置：[transport.rs:285](../../src/adapter/transport.rs#L285)、[transport.rs:305](../../src/adapter/transport.rs#L305)、[transport.rs:802](../../src/adapter/transport.rs#L802)、[input.rs:120](../../src/ui/input.rs#L120)。

`drain_lines` 每取一行都删除 Vec 前缀，反复移动全部尾部。大量短行可以在字节上限以内制造很大的 CPU 与分配开销。命令队列上限没有限制解析、错误响应和日志开销。接入循环会持续 accept 到 `WouldBlock`，连接数满后仍继续接入再丢弃；手柄事件循环也没有每轮上限。单轮成本不只取决于有效命令数。

**隔离基准证据：**同机 release 优化的切帧基准，16 次采样中位数如下；包含拆帧输出分配，不包含 JSON 解码、日志和 UI。数字受机器负载影响，不能直接换算为应用 FPS。

| 短帧数量 | 当前逐行删除 | 单次扫描原型 |
| ---: | ---: | ---: |
| 1,024 | 133 μs | 4 μs |
| 16,384 | 6,779 μs | 77 μs |
| 65,536 | 130,242 μs | 387 μs |

**建议：**游标扫描后只 compact 一次；为 accept、读取字节、解析帧、执行命令和手柄事件分别设定每轮额度。未处理内容留待下一轮，并轮换客户端起点，避免固定顺序饥饿。标记断开的连接应停止继续处理其剩余帧。

**验收：**保留 CRLF、半帧和超长帧行为；增加短帧突发、持续连接、慢消费者与多客户端公平性测试。测试检查预算和进展，不使用易受机器速度影响的严格毫秒阈值。

### F06 · P2 · 协议事件可能被归到后续 logical_step

位置：[state.rs:176](../../src/game/state.rs#L176)、[state.rs:184](../../src/game/state.rs#L184)、[transport.rs:267](../../src/adapter/transport.rs#L267)。

协议事件一直累积到 observation 发出才取走，而 logical_step 在这期间可多次变化。没有客户端或降低 observation 频率时尤其明显。限制为 4 个事件只限制容量，不能保证事件来自快照所表示的逻辑转移。

**复现证据：**第 1 步 hard drop 产生锁定事件，第 2 步 tick 后发出的 observation 标记为第 2 步，却带着第 1 步的事件。已有连续 5 次 hard drop 的测试只检查最终事件数为 4，没有验证事件与步骤的归属。

上游 [SPEC 的事件语义](https://github.com/lgn21st/tui-tetris/blob/main/protocol/adapter/SPEC.md)要求事件对应所表示的逻辑转移。

**建议：**让每次状态转移产生带 logical_step 的结果，包含该步事件与对应快照。需要合并 observation 时跳过完整旧步骤，不能把旧事件拼到新状态上。不要通过擅自扩展线上协议字段规避语义问题。

**验收：**覆盖多动作命令、多次固定步、无客户端后连接、observation 限频和慢消费者合并；每个快照的 events 必须来自该快照表示的转移。

### F07 · P2 · 空棋盘重启也改变 board_id

位置：[state.rs:232](../../src/game/state.rs#L232)。

`reset_with_seed` 无条件增加 board revision。对已经为空的棋盘重启时，锁定格没有变化，但 board_id 改变。

**复现证据：**新建空棋盘后以同 seed 重启，比较重启前后格子完全一致，revision 不同。上游 [SPEC](https://github.com/lgn21st/tui-tetris/blob/main/protocol/adapter/SPEC.md)把 board_id 的变化限定为锁定棋盘内容变化；episode_id 已承担局次变化的标识。

**建议：**基于实际棋盘内容变化更新 revision，审查所有 revision 写入路径；不要把重启、活动块变化与棋盘变化合并为同一种 invalidation。

**验收：**空→空不变，非空→空变化，活动块移动不变，锁定/消行按最终锁定棋盘变化更新。

### F08 · P2 · place 的 use_hold 执行两次 Hold

位置：[adapter/mod.rs:72](../../src/adapter/mod.rs#L72)。

规划前先把 Hold 加入 actions，又立即在工作副本上执行 Hold；随后执行 actions 时再次调用 Hold。第二次虽因 can_hold 已关闭而没有交换方块，但 action 入口仍推进 logical_step，导致一条命令多出一次状态转移。

**复现证据：**使用换入方块的当前位置作为合法目标，place 的 use_hold 路径推进 3 步，等效 Hold + HardDrop 只推进 2 步，最终棋盘相同。

**建议：**在工作副本上只执行一次 Hold，再执行规划动作和 HardDrop。保留失败时不提交副本的原子性，并检查 Hold 后游戏结束的情况。

**验收：**比较显式动作与 place 的棋盘、logical_step、piece/episode 元数据和事件；覆盖 Hold 不可用、空 Hold、非空 Hold、规划失败及 Hold 后结束。

### F09 · P2 · 设置面板和 Adapter 可以产生互相矛盾的运行状态

位置：[ui_state.rs:147](../../src/ui/ui_state.rs#L147)、[view.rs:187](../../src/ui/view.rs#L187)。

打开设置直接把 GameState.paused 写成 true，没有经过统一动作入口。Adapter 的 restart 或 pause 又可以使核心 paused=false，但 show_settings 仍为 true，UI 的额外条件继续阻止 tick。协议快照依据核心状态报告可玩，实际时间却不推进。

**复现证据：**临时 UiState 探针执行“打开设置→Adapter restart”，得到核心可玩而 UI tick 条件关闭的组合。该证据覆盖状态组合，尚非真实窗口的端到端实验。

**建议：**统一开始、暂停、重启、设置打开/关闭的生命周期处理；明确设置是否仅是 UI 覆盖层，以及远程 restart 应如何处理该覆盖层。将暂停的权威状态集中在运行时，避免 UI 字段形成另一个隐含暂停开关。

**验收：**设置开关与本地/远程 pause、restart、game over 的组合矩阵；快照可玩状态、实际推进与 UI 状态一致。

### F10 · P2 · 共享命令结构无法严格区分非法字段与 null

位置：[adapter/mod.rs:140](../../src/adapter/mod.rs#L140)。

action/place 共用含多个 Option 字段的结构体。即使拒绝未知字段，另一模式的字段也是这个 Rust 结构体的已知字段；传入 null 会变成 None，从而绕过基于 `is_some()` 的模式检查。

**复现证据：**action 命令带 `place: null` 可以被当前解析器接受，但上游 [schema](https://github.com/lgn21st/tui-tetris/blob/main/protocol/adapter/schema.json)的 action 结构不允许这个字段。

**建议：**按 mode 使用独立结构体/带标签枚举，保持字段存在性约束；从规范提取正反例语料，而非只测试能成功反序列化的常见命令。

**验收：**非法模式字段（包括 null）、字段混用、未知字段、restart 参数耦合、边界数值及已有有效命令。不要为了接受 null 放宽规范。

### F11 · P2 · 默认同步全量日志缺少磁盘与运行时成本上限

位置：[transport.rs:41](../../src/adapter/transport.rs#L41)、[transport.rs:718](../../src/adapter/transport.rs#L718)、[transport.rs:774](../../src/adapter/transport.rs#L774)。

Adapter 默认启用自动 wire log，并在同一轮询路径同步写文件。逐客户端记录 observation，没有轮转或总量上限。可被覆盖的 observation 在入队时就记录为 send，即使尚未真正发送，日志也不等于实际交付的线上帧。

**容量估算：**探针中的空棋盘 observation 为 1,971 字节，一条日志记录为 2,121 字节；若每秒发出 60 次，单客户端仅该类日志就约 458 MB/小时。实际值取决于频率、棋盘内容和连接数；没有客户端时不产生这一部分流量。

**建议：**将全量协议日志作为明确的诊断选项，或至少限制滚动文件总量；若异步写入，使用有界队列和明确丢弃策略，磁盘慢不能阻塞权威循环。区分入队、覆盖与实际发送，避免用入队日志证明客户端收到消息。

**验收：**磁盘慢/写失败/队列满时协议仍有进展，文件容量有界，日志语义可解释。此项属于已经存在的运行风险，审计没有进行长时间磁盘填充实验。

## 建议的目标架构

保持现有分层，在 UI 与 core 之间增加一个小而明确的运行时归属：

```text
键盘/手柄映射 ──┐
                ├─→ Runtime：生命周期、单调时钟、工作预算、动作顺序
Adapter 命令 ───┘          │
                          ▼
                    GameState / core rules
                          │ 每步结果：状态标识、事件、变化信息
              ┌───────────┼─────────────┐
              ▼           ▼             ▼
         UI 快照/动画   协议快照       有界音频效果
                          │
                   统一出站帧状态机
```

具体边界：

1. **Runtime** 决定何时处理外部输入、推进固定步和发布结果；不负责创建 UI 元素。注入单调时钟，区分调度时间与协议墙钟时间。
2. **GameState** 保留确定性规则，逐步收紧可写字段。状态转移结果明确说明步骤与事件归属，调用方不靠猜测给所有缓存标脏。
3. **Adapter transport** 处理连接、帧边界、背压和预算；只在完整帧边界选择发送优先级。
4. **UiState** 保留面板、动画和可视缓存；不独立决定核心是否推进，不直接任意改写核心字段。
5. **设备输入与纯输入逻辑** 分离。测试按键重复不应必须创建 Gilrs；设备泵有预算，映射与重复计算可独立测试。

实施顺序应先固定正确性契约，再搬迁职责，避免在大重构中改变可观察行为而难以定位原因。

| 核心构建依赖 | 规则代码虽不引用 GPUI，单 package 的非可选依赖仍让核心测试编译桌面栈。优先尝试默认 desktop feature、可选 UI/音频/手柄与 required-features；确有收益再拆 core crate。 | 中 |
| 放置搜索分配 | 每个节点创建小邻居 Vec，且使用多个映射容器。先改固定小数组/局部缓冲，再按 profile 决定是否复用工作区；复用核心碰撞/SRS 判定。 | 低，F08 先行 |
| 状态哈希覆盖 | 当前哈希未覆盖所有隐藏因果状态，如 RNG、上一动作旋转标记等。上游允许 opaque hash，因此不直接判为违约；若将其用作完整确定性状态身份，需定义并测试覆盖范围。 | 契约澄清 |

可优先清理的具体候选：

- `UiState.active_mask`：仅初始化/清空，没有生产读取。
- `UiState.last_action` 及服务于它的 `InputAction.record`、recorded/silent 区分：目前只有记录和对应测试，没有产品消费方；若不做动作历史可整条移除。
- `ClientState.requested_mode`：握手后保存但不读取。保留握手字段的解析/校验，删除无用持久字段。
- `game/input.rs::key_to_action`：实际 UI 使用另一路按键映射，仅测试调用它。合并到实际映射入口或删除，避免测试一套不用的规则。
- `GameState::is_lock_row`：仓库内无调用，其以方块原点判断的位置也不能替代 grounded。确认无外部 API 使用者后移除。

## 测试与维护改进

现有测试对核心碰撞、旋转、得分、计时和常见协议流程提供了有用覆盖。主要缺口在运行时与外部边界：

- 给 TCP writer 注入短写与 `WouldBlock`，不要只依赖 localhost 通常一次写完的行为。
- 将时钟注入超时和调度测试。当前 observer 测试使用很短的真实超时，且在控制端握手前已建立 observer；负载波动可能导致 observer 先超时。本轮该测试通过，此前会话曾遇到超时，并非本轮失败。
- 测试端 `try_read_json_line` 使用局部缓冲区，读到半行后超时会丢弃已读内容；改为跨调用保留缓冲区，避免测试工具自身制造半帧错误。
- 对模式命令使用 schema 正反例；对 board_id、logical_step 和 events 增加跨路径的一致性断言。
- 输入重复逻辑与真实设备初始化分离；窗口激活做少量集成测试，纯规则用可控事件序列。
- 音频增加有意义的混音输出测试：饱和/裁剪、voice 终止、声道映射与事件预算；没有必要给简单转发方法逐个补测试。
- 维护 `docs/adapter_acceptance.md` 时标明证据层级，不能把普通 TCP happy path 当成背压和半帧符合性的证明。
- 修复运行时、暂停和日志策略后同步更新架构与 implementation profile；不要复制上游规范来掩盖差异。

## 实施批次与完成标准

1. **传输正确性与成本上限**：F01、F05、F11。短写测试先行，统一 in-flight 帧，线性切帧，工作预算和有界日志；确认慢客户端不影响其他客户端。
2. **核心与协议一致性**：F06、F07、F08、F10。逐项添加能在当前实现失败的回归测试，再修改实现；保持 place 原子性和现有合法命令兼容。
3. **运行时归属与输入生命周期**：F02、F03、F04、F09。独立时钟和 pump，统一暂停语义，窗口激活输入策略；加入无窗口集成测试和实际窗口验证。
4. **精简与按测量优化**：删除确认无消费方的字段/映射，收紧核心写接口，优化 HUD、音频和构建依赖。记录分配、帧成本或构建时间的前后证据后再扩大改动。

每批执行项目既有测试、Clippy、doc tests、fmt 和 diff 检查。最终再执行 release bundle，从源码目录之外启动，验证资源、图标、声音、输入、缩放和后台 Adapter 行为。不要用“能编译 release”替代运行时验收。
